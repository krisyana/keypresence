# ADR-0002: Authentication and sessions

Status: accepted

## Decision
- Email + password. Passwords hashed with **scrypt** (Node built-in, N=2^15, r=8, p=1, 16-byte salt, 64-byte key), stored as `scrypt$N$r$p$salt$hash`, compared with `timingSafeEqual`.
- Server-side sessions: a random 32-byte token is sent in an `HttpOnly; SameSite=Lax; Path=/` cookie (`Secure` when `APP_URL` is https). Only the **SHA-256 of the token** is stored (`sessions.token_hash`), so a database leak does not yield usable sessions. 12-hour sliding expiry, 30-day absolute.
- Roles: `admin`, `employee`. Authorization is a middleware (`requireRole`) applied to route groups; the admin router is mounted behind it as a whole, so a new admin route cannot forget the check.
- CSRF: mutating requests must be `application/json` (not a "simple" form content type) and, additionally, the `Origin` header, when present, must match `APP_URL`/host. `SameSite=Lax` covers the rest.
- Login rate limit: in-memory sliding window per (email, IP): 10 attempts / 10 minutes. Unknown email and wrong password return the same error and do similar work (dummy hash).

## Why not JWT sessions
Revocation (deactivate an employee, rotate on password change) must be immediate; a stateful session is one `DELETE`. There is a single backend, so statelessness buys nothing.

## Why not passkeys / OAuth now
Better, but a demo that must run offline with fictional users needs a local credential. The auth module is isolated so a provider can be added.

## Consequences
In-memory rate limiting is per process (documented limitation). Passwords in seed data are fictional and printed by the seed script only.
